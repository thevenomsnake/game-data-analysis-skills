# 数据报告核心结论写作手册

> 文档类型：使用手册
>
> 适用范围：数据日报、周报、月报的群发结论
>
> 最近验证：2026-08-10

本手册用于把完整报表压缩成可直接发群的核心结论。目标是让读者迅速知道整体处于什么状态、发生了什么变化、哪些问题需要处理。完整不等于把所有指标写一遍。每个数字都应当帮助读者理解一个判断。

## 1. 收到报告后先归档

附件到达后，立即把原始报告复制到项目目录，再开始分析。不要依赖 Downloads、OneDrive、临时目录或聊天记录保存历史。

建议按报告结束日期归档：

```text
outputs/weekly-report-history/<YYYY-MM-DD>/
  report.html   原始报告
  data.json     报告内嵌的结构化数据
  summary.md    已确认结论和业务口径
  evidence/     用户补充的截图或业务证据
```

原始报告负责复核，`data.json`负责跨期计算，`summary.md`负责保存经过业务确认的解释。下一期比较时同时读取数据和已确认口径，不能只看上次文案反推定义。

## 2. 先定比较口径

动笔前先区分四类时间口径：

- 整体累计，用于回答总规模和当前累计表现。
- 完整周期，用于周环比或月内阶段比较。
- 不完整周期，只使用日均、最新单日或明确标注的事件窗口。
- 可计算日期范围，用于留存等需要等待观察期的指标。

完整7天和不足7天的累计值不能并列比较。月末或版本窗口不足一周时，用日均和最新单日描述趋势；只有事件分析需要时，才单独给出窗口累计值。

累计表不自动代表本周变化。渠道累计质量、累计LTV、累计用户结构等指标，只能写成当前整体结构；没有按日或按周数据时，不能描述为本周上升、下降或分化。

## 3. 每部分先回答整体情况

每个模块按读者的理解顺序组织，具体内容可以省略，但已有内容不要颠倒：

1. 整体处于什么状态。
2. 常规结构和阶段变化是什么。
3. 哪个长期问题最值得关注。
4. 版本、活动、异常等特殊事件带来了什么变化。
5. 已采取什么动作，或下一步要做什么。

整体结果和常规结构构成主盘，长期问题说明持续风险，特殊事件负责解释偏离主盘的变化。不要用异常、渠道或单日事件开场，也不要把特殊事件插在常规结构中间。读者应先知道总规模和主趋势，再进入结构拆分。

### 新进

先写累计来量和完整周变化，再写近期日均与最新单日。随后交代核心来量渠道的规模、集中度和LTV，再写整体用户结构、漏斗异常和处理进展。新进模块固定使用“整体来量、核心渠道、用户结构、漏斗异常、处理进展”的顺序。

### 留存

整体留存与首发日留存并列呈现，并明确当前可计算到哪一天。随后用一阶、二阶登录比说明整体留存链路，再按端、用户类型和渠道拆分重点人群。留存模块固定使用“整体留存、登录比、重点人群”的顺序。

### 活跃

先用各完整周的日均活跃说明整月走势，再写版本更新等特殊事件带来的局部变化。随后说明当前稳定水平，并用入水口、净流出和缺口判断后续风险；已经明确需要拉回流时，把动作写进结论。双栖等用户结构放在最后，不打断活跃主趋势。活跃模块固定使用“完整周走势、版本影响、当前状态与出入水口、用户结构”的顺序。

### 商业化

先写累计流水和完整周期贡献，再写常规卡池、商品或BP结构及其长期问题，最后补版本、礼包或联动带来的阶段性变化。时间同时发生不能直接证明因果，归因必须结合实际上线内容和用户补充信息。

### 模式及养成

模式渗透、时长占比和养成深度分开描述。用户时长分布右移，不等于同等时长下养成更深。需要同时检查人群在时长区间中的移动，以及相同区间内等级达成率的变化。

## 4. 核心结论的取舍

一段只承担一个主要判断。一个判断通常保留一至三个数字：

- 一个数字说明当前水平。
- 一个数字说明变化幅度。
- 必要时再用一个数字说明结构差异或风险边界。

多个指标表达同一件事时，保留最直接的证据。例如版本更新后首日进度下降，可以用“未进入任意模式占比”和恢复状态说明；其他同步变化只有在改变判断时才加入。

内部核算需要的字段不自动进入管理层结论。商品道具、技术实现、埋点路径和计算过程只有在改变业务判断时才保留；其余内容留在数据证据和口径说明中。购买路径等内部口径仍要先核对准确，不能因为最终文案不展示就忽略。

核心结论需要满足至少一项：

- 改变对整体状态的判断。
- 说明趋势已经加速、放缓或反转。
- 暴露重点人群、渠道或阶段的显著差异。
- 解释版本、活动或商品带来的结果。
- 指向已经采取或需要采取的动作。

只补齐表格、解释分析过程或重复同一判断的数字应删除。

业务前提不能当结论重复。

## 5. 结构差异与业务口径

分端、分渠道、分用户类型时，先写比较结论，再给关键数据。不要因为某个群体符合传统认知，就默认它质量更高。留存、付费和LTV可能指向不同结论，应分别说明。

百分比必须说明分母。购买路径互斥时，要先确认每组代表的最终状态，再解释占比。整体占比、购买者内占比和高消费人群内占比不能互换。

异常归因至少要区分三件事：

- 数据口径或上报是否发生变化。
- 版本是否改变了用户流程或玩法。
- 同期是否上线礼包、卡池或活动。

无法区分时写成待确认问题，并补充当前处理状态，例如“已与合作方沟通，等待答复”。

## 6. 表达密度

群发结论不复述完整报表。每个模块优先控制在一至三段，每段一至三句。压缩不能变成数据速记，句子仍要包含对象、变化和结论。

推荐写法：

```text
整体规模和主趋势。关键结构或异常及其幅度。处理状态或下一步动作。
```

删除这些内容：

- 与完整周期不可比的局部累计值。
- 已被另一项指标充分表达的关联数据。
- 没有业务意义的小数变化。
- 仅凭时间先后作出的因果判断。
- “需要关注”“可能有影响”等没有对象和行动的空泛提醒。

## 7. 交付前检查

- 第一段是否先说明整体情况。
- 周期是否完整且可比，不完整周期是否改用日均或最新单日。
- 累计指标是否被误写成本周变化。
- 每段是否只有一个主要判断。
- 每个数字是否直接支撑该判断。
- 留存是否区分整体、首发日和当前可计算日期范围。
- 分端、分渠道、分类型是否使用同一指标和同一口径比较。
- 商品、道具、BP路径和人群分母是否准确。
- 版本或活动归因是否有业务事实支持。
- 已有处理动作是否写入结论。
- 删除任意一句后若判断不受影响，该句是否应该删除。
